Part 1

1. Executive Summary — What AEGIS Actually Is

The problem

Autonomous AI agents are starting to take real-world actions on someone's behalf — buying things, subscribing to services, paying other agents. The moment an agent can initiate a payment, "who is this agent" (authentication) stops being the interesting question. The interesting question is: what, specifically, is this agent allowed to do right now, within what limit, granted by whom, and can that be taken back instantly if something looks wrong? An API key answers the first question. It says nothing about the second.

What AEGIS actually controls

AEGIS sits between an agent's decision to act and the money actually moving. Every agent holds a cryptographic capability token (not a raw credential) with a maximum amount, currency, allowed categories, and allowed payment rails baked into the token itself. That authority can be narrowed further — delegated to a sub-agent with tighter limits (attenuation), and bounded again to one specific, budgeted objective (a mission). Every transaction is evaluated against all of these boundaries before anything executes, the outcome is one of three verdicts (ALLOW / DENY / ESCALATE), and every step — not just the final outcome — is written to a signed, hash-chained ledger that a completely separate tool can verify without trusting AEGIS's own code.

The three words, precisely

WordWhat it means in this implementation, specifically
BoundedA capability token's caveats (amount, currency, categories, rails, expiry) are enforced by the token's own cryptographic structure (a Biscuit authorizer check), not a database flag an application could quietly ignore. A mission narrows further, on top of the token, never past it.
RevocableRevoking one agent marks its token identifier revoked; every descendant token's verification checks its full ancestry, so revoking one node fails every token derived from it on its very next use — no separate cascade step to run.
VerifiableEvery ledger entry is Ed25519-signed and hash-chained to the one before it. A standalone tool (verifier/) that imports nothing from AEGIS's own code can independently re-derive whether that history is intact, from only an export file and AEGIS's public key.

A. The 20-second explanation

"AEGIS gives an AI agent a cryptographic permission slip instead of a password — one with a spending cap, a category list, and an expiry baked in. That permission can only get narrower as it's handed down to sub-agents, it can be revoked instantly and the revocation actually sticks, and every decision is recorded in a way that can be checked afterward by a tool that doesn't trust AEGIS itself."

B. The 60-second explanation

"Once an agent can spend money for you, checking a single transaction against a rule isn't enough — you need to know it can still only spend what it was actually delegated, that you can cut off its authority instantly and have that actually propagate to everything it delegated further, and that you can prove afterward nothing was tampered with. AEGIS answers all three. Authority is a signed capability token, not a config value — it narrows every time it's delegated and can never widen. A mission layers a bounded objective and its own budget on top of that token. Every transaction runs through a real decision pipeline — mission budget gate, capability check, risk evaluation — and resolves to allow, deny, or escalate, never a silent default. Revoking an agent cuts off every sub-agent beneath it, instantly, with no cleanup step. And every decision — not just successful ones — is written to a hash-chained, signed ledger that a separate, independent tool can verify without trusting a single line of AEGIS's own code. That's the whole system: bounded, revocable, verifiable."

Why authentication alone is insufficient

Authentication answers "is this really agent X." It says nothing about whether agent X's this specific request — $380, category flights, counterparty acme-airlines, right now — is something X was actually delegated to do. A stolen or over-trusted API key is authenticated perfectly and can still do anything the backend allows. A capability token collapses "who" and "what, exactly, up to how much" into one cryptographically checkable object, so the answer to "is this allowed" never depends on trusting an application's own bookkeeping.

Part 5 — The Heart of AEGIS

5. Authority — Deep Explanation

Every agent's authority is a Biscuit capability token — a signed, self-contained credential whose caveats (max amount, currency, allowed categories, allowed rails, expiry) are checked by a cryptographic authorizer, not by an application trusting its own database. Root authority is minted at agent creation. Delegation (attenuate) mints a child token from a parent's. Attenuation is the mathematical property that makes delegation safe: a child token's caveats can only be equal to or narrower than its parent's, in every dimension, simultaneously.

Revocation propagation

Revoking travel-agent (the root, above) does not touch flights-only's stored token at all — nothing is edited, deleted, or pushed to it. What changes is that flights-only's next verification includes checking its ancestor chain, and the root is now marked revoked. That single check is what fails — instantly, for every descendant, with no enumeration of "which sub-agents does this affect."

6. Missions — Deep Explanation

Why missions exist if capabilities already exist

A capability token bounds what an agent could ever do, in general, for its entire lifetime — its ceiling. A mission bounds what an agent is doing right now, for one objective — a cumulative budget spent across possibly many transactions, plus optional narrower category/counterparty restrictions, with its own expiry. An agent with a $5,000 standing token might be given five different $500 missions over time, each one auditable and revocable independently of the others and of the token itself. Without missions, every transaction would only ever be checked against the same broad, unchanging ceiling — there would be no way to express "for this specific purchase run, no more than $800, only flights, only this vendor."

Which mission limits exist

  • Budget — a cumulative cap (budgetMinorUnits), enforced as spent + reserved + requested ≤ budget.
  • Currency — must exactly match the underlying token's currency.
  • Allowed categories — optional; if set, must be a subset of the token's own categories.
  • Approved counterparties — optional; missions can restrict counterparties even though the token itself has no counterparty concept at all.
  • Expiry — must not be later than the token's own expiry.

Missions do not declare a rail restriction — rail allowlisting remains entirely the token's concern (src/mission/policy.ts's own doc comment is explicit about this).

What if the mission allows something the token doesn't — or vice versa?

Effective permission = intersection of boundaries

This is enforced two ways, not one. At mission-creation time, validateMissionAgainstToken() rejects outright any mission whose currency doesn't match, whose categories aren't a subset of the token's, or whose expiry is later than the token's — so a mission wider than its token cannot even be created. At transaction time, both checks still run independently anyway (mission gate, then capability/policy) — so even if a mission's stored constraints were somehow looser than the token (they structurally can't be, but the runtime doesn't assume that), the token's own check still applies on top. There is no code path where a transaction is allowed because the mission alone said yes; both boundaries must agree.

Which one is checked first — and why it's not just "either"

The mission gate (checkMissionGate) runs before decideTransaction's capability/policy check, in the route handler. Order: mission status → counterparty allowlist → category allowlist → budget, then capability/policy, then risk. This is deliberate: the mission gate is the cheapest, purely local check (no cryptographic verification, no network), so a mission-scoped denial short-circuits before the more expensive capability check ever runs.

Six scenarios, exact manual test procedure

Scenario A — Valid transaction → ALLOW

Setup: agent with token cap ≥ amount, optional mission with budget ≥ amount.
Input: Amount 380 · Category flights · Rail mock_x402 · Counterparty acme-airlines (must match mission's allowlist if one is attached).
Expected: Every pipeline stage green, execution stage shows a real mockx402_… settlement reference.

Scenario B — Over mission budget → DENY

Setup: same mission as above, already has some spend.
Input: Amount larger than remaining budget (e.g. 5000 against an $800 mission).
Expected: DENY at the mission-gate stage — reason text: "Transaction would exceed this mission's budget (spent so far: X, requested: Y, budget: Z)". Capability/risk stages never run.

Scenario C — Wrong category → DENY

Input, mission attached: a category not in the mission's allowedCategories → mission-gate reason "Category "X" is not in this mission's allowed categories (…)".
Input, no mission (standing authority only): a category not in the token's own allowlist → the capability layer's Biscuit authorizer itself rejects it; the surfaced reason is a raw "Failed check(s): …" string derived directly from the failed Biscuit rule, not a hand-written sentence — a real, technically interesting detail: the token's caveats are enforced by the cryptographic authorizer, not application code translating them into English.

Scenario D — Invalid / revoked authority → DENY

Setup: a valid agent, then revoked (Authority → Revoke, or the Security workspace's scenario).
Input: the exact same transaction that succeeded before revocation.
Expected: DENY at the capability stage — reason text: "Token (or an ancestor) was revoked at <timestamp>: <reason>".

Scenario E — Behavioral anomaly → ESCALATE

Setup: a fresh agent with no mission attached (standing authority). Submit three transactions at a small, consistent amount (e.g. $50) to build history.
Input: a fourth transaction at more than 3× that mean (e.g. $600 against a $50 mean = 12×).
Expected: ESCALATE — reason: "Behavioral anomaly detected: Amount (X) is N.Nx this agent's historical average (Y), over the 3x threshold". The Decision Inspector's Intent: line still shows consistent — it is the behavioral layer alone that forced this, independent of the intent judge.

Scenario F — Execution / rail mismatch or failure

The mock_x402 rail has a fixed price catalog (acme-airlines:flights = $380, acme-hotels:hotels = $210, cloudco:software = $1500). An amount that doesn't match the quoted price for that counterparty/category fails at settlement even after an ALLOW verdict — this is a genuine, reproducible execution-layer failure, not a policy denial. It's a good answer if a judge asks "what happens if the rail itself rejects something policy already approved" — but not a headline demo beat; mention it only if asked.

ESCALATE, precisely

Why it exists: not every risky-looking transaction is actually invalid — an unusually large purchase might be entirely legitimate. Escalate is the verdict for "policy has no objection, but this doesn't look like this agent's normal behavior, so don't execute silently." How it differs from deny: a deny means a hard boundary was crossed (budget, category, revoked authority) — deterministic and non-negotiable. An escalate means every deterministic boundary was satisfied, and the risk layer alone raised a flag. Does it stop execution? Yes — identically to deny, nothing executes on escalate in the current implementation. What risk condition triggers it, in the reproducible demo path: the behavioral-baseline heuristics in src/risk/baseline.ts — a rate spike or an amount far outside this agent's own history. Is Anthropic involved in demo mode? No — the intent judge in demo mode always returns "consistent"; it is architecturally impossible for the demo-mode intent judge to be the reason for an escalation. Every reproducible escalation in this environment comes from the deterministic, disclosed behavioral layer, never from AI judgment.

Implying that "the AI decided to escalate this" in demo mode — it did not; the demo-mode judge cannot produce that verdict at all.
Implying escalation pauses for a human reviewer to click approve/deny somewhere in this build — that workflow is not implemented; escalate currently means "verdict returned, not executed," full stop.

9. AI / Anthropic — Where Intelligence Actually Lives

Demo Mode — what actually happens

AEGIS_DEMO_MODE=true swaps the intent judge for createDemoIntentJudge() (src/api/demoMode.ts) — a fixed function that performs no analysis and always returns verdict: "consistent", with a rationale string that says, verbatim, "This is not a real AI risk evaluation and must never be used in production." This isn't a UI label bolted on top — it's the literal text returned by the judge function itself, visible in every Decision Inspector.

Non-demo / intended live mode — where Anthropic is used

Outside demo mode, createServerIntentJudge() requires a real ANTHROPIC_API_KEY and constructs AnthropicIntentJudge (src/risk/anthropicJudge.ts) — a real model call comparing the agent's delegated goal against the transaction's stated purpose, returning a structured consistent/inconsistent/ambiguous verdict with a rationale. This code path exists and is tested (anthropic-judge.live.test.ts, excluded from the default npm test run because it needs a real key) — it has simply not been exercised with a real credential in this environment.

What the LLM/risk judge evaluates — and what it never touches

Probabilistic judgment may assist risk/intent evaluation, but deterministic authority and budget enforcement are not left solely to the model. The intent judge — real or demo — only ever answers "does this transaction's stated purpose look consistent with the agent's delegated goal." It has no path to widen a capability, approve an over-budget transaction, or override a policy denial. Mission budget math (src/mission/reservation.ts), capability/caveat verification (src/capability), and revocation checks (src/capability/authorize.ts) are pure, deterministic, synchronous code — no model call, no network dependency, no possibility of a hallucinated exception. decideTransaction()'s own ordering guarantees this: policy runs first and can only make the outcome stricter for risk to act on, never the reverse.

This is safer specifically because a model's judgment is probabilistic and can be wrong in either direction (too permissive or too strict) — keeping the actual money boundary (amount, category, revocation) in deterministic code means a bad or manipulated model output can, at worst, escalate a transaction for review; it cannot authorize spend outside the token's own bounds.

Why demonstrate in deterministic mode — said as a deliberate choice, not an apology

  • Reproducibility — the same input always produces the same verdict, so a rehearsed demo behaves identically every time.
  • No external dependency — no network call, no API-key provisioning, nothing that can fail for reasons outside AEGIS's own code during a live presentation.
  • No provider latency risk — a demo running on a conference room's wifi shouldn't be at the mercy of a third-party API's response time.
  • No real money movement — the mock rail is self-built and loopback-only by construction; nothing here could accidentally charge a real card even if misconfigured.
We're demonstrating in a mode that removes every external dependency on purpose — so what you're seeing is entirely the software pipeline, not the reliability of a third-party API on the day we happen to be presenting.
Part 10 — Hero Technical Section

10. Concurrent Budget Race

The attack, and why naive systems fail it

A spending limit implemented as "read the current spend, check it against the budget, then write the new spend" has a gap between the read and the write. If twenty requests hit that gap at nearly the same instant, every one of them can read the same "budget not yet exceeded" state and all twenty can proceed — a classic check-then-write (TOCTOU) race. A budget boundary that only holds under sequential testing hasn't actually been proven to hold at all; concurrency is precisely the condition most systems never load-test for.

What AEGIS does instead

Atomic reservation: src/mission/reservation.ts's reserve() is a single SQL UPDATE that computes budget − reserved − settled ≥ requested and increments reserved_minor_units in the same write — there is no separate read step for another request to race against. The database's own transaction isolation, not application-level locking or request ordering, is what decides which requests succeed. State protected: the mission's reserved_minor_units and budget_minor_units columns in SQLite (src/state/db.ts).

Why sequential testing would not prove the same property

Firing 20 requests one after another, waiting for each response before sending the next, never exercises the actual race window at all — every request would see a fully up-to-date budget by construction. The Security workspace's attack fires all 20 genuinely concurrently (no waiting between dispatches) specifically so the atomic reservation is under real contention, not simulated contention.

Verified demo numbers (reproduced in this handbook's own verification pass)

20 concurrent attempts  ×  $380 each  against a $2,000 mission budget
↓
5 allowed  ·  15 blocked  ·  $1,900.00 spent  ·  $0.00 overspend

The exact split (how many of 20 land as allowed) depends only on the mission budget and the per-attempt amount shown on the Launch-attack button — it is recomputed live by the server every run, not a fixed constant in the UI. The invariant that must always hold, regardless of the split: allowed × amount ≤ budget, and allowed + blocked = attempts.

What to point at / what to say

Limits are easy to enforce sequentially. The interesting question is whether they survive contention. Twenty requests can arrive at once — a budget boundary is only meaningful if it survives that, not just the common case where requests politely take turns.

Point at the per-attempt ✓/✗ grid first (it's visually immediate), then the four stat numbers, then the green banner's exact spend figure last — that ordering builds from "something happened" to "here's the proof it was exactly correct."

Why a technical judge should care: this is a real, load-tested concurrency guarantee backed by an adversarial test in the suite (src/mission/__tests__/mission-reservation.test.ts) that fires genuinely concurrent calls and asserts on final server state — not a claim resting on the demo alone.

12. Evidence / Ledger — Deep Explanation

What gets recorded

FieldWhat it is

content_hashA hash of this entry's own content.
signatureEd25519 signature over the entry, produced by the server's ledger signing key.

How verification works

verifyChain() walks every entry in sequence and confirms three things simultaneously: (1) each entry's content_hash actually matches its stored content — catches direct data tampering; (2) each entry's prev_hash matches the actual previous entry's content_hash — catches a broken or reordered link; (3) each entry's signature verifies against the ledger's known public key — catches a forged entry signed with a different key. All three are independently tested (src/state/__tests__'s "hash-chained ledger — tamper detection" suite covers each category separately).

Why normal application logging is not equivalent

A normal log is a record the application chooses to write, in a form the same application (or anyone with database access) can also silently edit afterward with no trace. A hash-chained, signed ledger makes any retroactive edit — however small — break a verifiable mathematical relationship, not just "look suspicious." The difference isn't that the ledger is harder to edit at the storage layer (it is, in fact, the exact same SQLite file, editable the same way) — it's that editing it without also correctly recomputing every subsequent hash and re-signing with a key you don't have is what becomes detectable.

Honest framing, precisely: this is not "append-only, tamper-proof infrastructure" — the underlying storage can be modified directly (that's exactly what the tamper demo does). What's actually true is narrower and still strong: modification becomes detectable, both by AEGIS's own check and by a completely independent tool.

Part 14

14. Independent Verifier

Why the dashboard shouldn't verify itself

If AEGIS's own server were the only thing that ever confirmed the ledger's integrity, a compromise of that server's own verification code could hide a compromise of the ledger it's checking — the fox checking its own henhouse. verifier/ is a genuinely separate tool: it imports nothing from src/, and depends on nothing running at all — it operates entirely offline against a static export file.

What's independently verified

  • The full hash chain's integrity (re-derived from scratch, not trusting AEGIS's own verifyChain() result).
  • Every signature, against AEGIS's public key only.
  • Whether any mission's settled spend, reconstructed independently from the exported ledger entries, ever exceeded that mission's own budget.

Inputs it needs

An exported ledger file (verifier/dist/export/exportLedger.js <db path> <publicKeyHex> <output>) and AEGIS's public key, printed by the server's own startup log. Nothing else — no database access, no running AEGIS process, no trust in AEGIS's own reporting.

What success/failure means

Exit code 0: every entry's hash, chain link, and signature check out, and no mission's reconstructed spend exceeds its budget. Exit code 1: at least one of those failed — the tool names which. Both are real, observable in a terminal, not narrated claims.

How to run it / demonstrate it

npm run build:verifier
node verifier/dist/export/exportLedger.js ./aegis.db <publicKeyHex> ledger-export.json
node verifier/dist/cli.js ledger-export.json

Run this in a terminal after the tamper demo, against a fresh export taken post-tamper, if time permits — showing exit code 1 from a tool that has never touched AEGIS's own code is the strongest possible closer for a technical judge, but it is optional and time-boxed; the in-dashboard tamper demo alone already lands the point.

Positioning

This is the trust property that makes the whole system's "verifiable" claim credible rather than self-reported: AEGIS isn't just checking its own homework — a second, independently-authored program reaches the same conclusion.

Part 19

19. Questions Judges May Ask

"What prevents the agent from just bypassing AEGIS?"

In this architecture, nothing prevents a rail credential from being called directly by something that isn't AEGIS — AEGIS is the decision layer, not a network firewall. What it does guarantee is that if a rail adapter only ever receives credentials scoped to it and is only ever invoked through AEGIS's own execution path, no valid capability token exists that could authorize the bypassed path either.

Precisely: AEGIS never holds the rail's own settlement credentials for the agent's use directly — the agent has no rail credential to use standalone. Full production-grade isolation of "the agent literally cannot reach the rail except through AEGIS" is an infrastructure/network-boundary concern, named in docs/SYSTEM_ARCHITECTURE.md §7 as separation of decision and custody, not fully solved at this MVP stage.

Don't say: "It's impossible." Say: "the agent is never handed a credential that lets it bypass this."

"Why not just use API keys?"

An API key answers "who is this," not "what, exactly, up to how much, is this specific request allowed to do." A capability token encodes the boundary itself, cryptographically — the check doesn't depend on trusting an application's own bookkeeping of what that key is "supposed to" be limited to.

A leaked or over-trusted API key can do anything the backend permits for that key's role. A leaked capability token can do exactly what its own caveats say, and revoking it takes effect immediately on the next verification.

"How is this different from RBAC?"

RBAC assigns a role, and the role's permissions live in a central table someone can edit. Here, the permission set travels inside the credential itself, is mathematically bounded by its parent at mint time, and needs no central lookup to verify.

RBAC roles are typically coarse and shared across many principals; attenuation produces a unique, narrower-every-time token per delegation, verifiable offline from the token alone (plus revocation state).

"Why use capability tokens specifically?"

Because the property we need — "this credential can only ever narrow as it's delegated further" — is exactly what capability-based security with attenuation is designed to guarantee, and Biscuit gives us that with real cryptographic enforcement rather than a convention.

"What happens if the agent is compromised?"

Its blast radius is exactly its token's own bounds — the max amount, categories, and rails it was actually delegated, nothing more — and it can be revoked instantly, cutting off it and everything it delegated further.

Don't say: "nothing bad can happen." Say: "the damage is capped by design, and stoppable instantly."

"What prevents budget race conditions?"

One atomic SQL statement that checks and reserves budget in the same write — see Part 10. Demonstrated live under 20 genuinely concurrent requests.

"What does ESCALATE actually do?"

Stops execution, exactly like deny, but for a different reason: every hard policy boundary passed, and a separate risk signal (behavioral anomaly, or an inconsistent/ambiguous intent judgment) flagged it anyway. See Part 8.

Don't imply a human-approval workflow exists to click "approve" on an escalated transaction — that's not built; escalate currently means "returned, not executed."

"Where is AI used?"

In the intent-consistency judge only — comparing an agent's delegated goal against a transaction's stated purpose. In this demo it's a disclosed deterministic stand-in; the real Anthropic-backed version exists in code and requires a credential we're not using for this presentation. See Part 9.

"Why Anthropic?"

It's the model provider the risk-judge interface is built against in this codebase; the interface itself is pluggable, so swapping providers is an adapter, not an architecture change.

"Why not use the LLM for all policy decisions?"

Because a model's judgment is probabilistic and can be wrong in either direction. Budget, category, and revocation enforcement are deterministic code specifically so a bad or manipulated model output can, at worst, cause an unnecessary escalation — never an unauthorized spend.

"What happens if Anthropic is down?"

safeJudge() treats a judge failure/timeout as "unavailable", which combineRiskSignals() maps straight to escalate — fail-safe, not fail-open. Demo mode is unaffected either way, since it never calls a real model.

"Is real money moving?"

No. This demonstration runs in AEGIS_DEMO_MODE=true, which registers only a self-built mock payment rail — no real rail is reachable in this mode regardless of configuration.

"Where is Razorpay in this?"

Razorpay is the buildathon this was built for — there is no Razorpay API integration in the current codebase. The rail layer is adapter-based by design (a Stripe test-mode adapter and a self-built mock adapter both exist today); adding a Razorpay adapter is architecturally the same shape of work as either of those, not a redesign.

Never say "we integrate with Razorpay" — we don't, and shouldn't imply it.

"Is this production-ready?"

No, and we say so directly — this is a from-scratch technical demonstration. It hasn't been load-tested at real scale, integrated with a real agent framework, or exposed to real users or real money. See docs/SECURITY_MODEL.md's limitations section for the full, specific list.

"Can authority be widened?"

Not through attenuation — structurally impossible, enforced before a wider child token is ever minted. The only way to grant more authority is to mint an entirely new, independent root token.

"What happens if a parent is revoked?"

Every descendant fails its next verification — see Part 11.

"Can the database be tampered with?"

Yes, directly, at the storage layer — we don't claim otherwise. What we claim, and demonstrate live, is that such tampering becomes detectable, both by AEGIS's own check and by a completely independent verifier.

"Is the ledger a blockchain?"

No. It's a hash-chained, Ed25519-signed append log with one trusted signer (the running process's own key) — tamper-evident, not distributed consensus. We're explicit about this distinction in our own docs.

"Who verifies the verifier?"

Its own test suite — 58 tests, run independently of the main suite — including adversarial cases where it must correctly refuse to certify a tampered or incomplete export rather than guessing. Anyone can also read its ~150 lines of core logic themselves; it deliberately imports nothing from AEGIS to keep that read small.

"Can someone steal a capability token?"

A stolen token can be used up to exactly its own bounds until revoked — same category of risk as a stolen scoped credential in any capability system. Revocation is instant once detected. Full token-storage hardening (e.g. how a real agent framework would store these client-side) is outside this MVP's scope.

"How would you deploy this in production?"

The application itself needs no architecture change — it's a normal long-running Node/Express process. render.yaml in this repo is a verified-locally Render Blueprint for exactly that; it has not been deployed to a public URL. Production hardening beyond deployment — HSM-backed signing keys, real credentialed rails, load testing — is explicitly named as future work, not claimed as done.

"What's the biggest limitation?"

Be honest, pick one that's actually true and interesting: tail truncation of the ledger (deleting the most recent entries) is not detectable from a single snapshot — there's nothing after the cut to contradict. Or: no real AI risk evaluation or real payment has been exercised in this environment, by design, for this demo.

"What's actually novel here?"

Not any single primitive alone (capability tokens, hash chains, and atomic reservations each exist elsewhere) — the composition: authority that provably narrows through delegation, bound again to a mission, checked through a pipeline that keeps deterministic boundaries out of AI's hands, revocable instantly, and independently verifiable afterward, all in one coherent, working system.
